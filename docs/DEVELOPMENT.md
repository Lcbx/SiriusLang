# Compiler development

The compiler is implemented in **Sirius**, with native imports rooted at
`src/modular_cli.sirius`. `bootstrap/compiler.c` is the committed C11 seed;
it is generated by the MIR C backend, not independently maintained. The old
Python compiler, flat source manifest and AST-to-C emitter are retired.

Python 3.10+ is used for build and test orchestration. Build scripts detect a
C11 compiler; native executables can be used without Python after building.
All commands below run from the repository root.

## Build tools

| Command | Purpose |
| --- | --- |
| `python tools/build_compiler.py` | Build `sirius` from committed C |
| `python tools/build_mir_runner.py` | Build `sirius-run` interpreter and package CLI |
| `python tools/build_modular_compiler.py` | Build `sirius-modular` from native source modules |
| `python tools/build_modular_runner.py` | Build `sirius-run-modular` |
| `python tools/build_module_scanner.py` | Build standalone native source-module scanner |
| `python tools/generate_bootstrap.py --check` | Verify committed C against the self-hosting fixed point |
| `python tools/generate_bootstrap.py` | Regenerate committed bootstrap C; does not run all fixtures |

If new compiler features are not accepted by the previous C seed, first
implement them using the *old* accepted Sirius subset, regenerate the seed,
then adopt the new syntax in compiler sources.

## Test runner

```sh
python tools/test_all.py --group smoke --fail-fast
python tools/test_all.py --group frontend --fail-fast
python tools/test_all.py --group mir --fail-fast
python tools/test_all.py --group modules --fail-fast
python tools/test_all.py --list
python tools/test_all.py                      # entire active suite; expensive
```

The suite prepares one shared MIR runner before the first selected driver that
requests it. Setup time is printed separately from individual test timings.
Each test receives the same suite-local executable, including tests without a
`--runner` option. A suite using only smoke checks does not build a runner, and
`--list` never builds one. The content-addressed cache keeps the original binary
for later suites; the suite-local copy survives cache resets during tests and is
removed when the suite finishes.

To select an existing executable instead of building the shared runner:

```sh
python tools/test_all.py --runner ./sirius-run
```

Standalone drivers retain their usual cache behavior. Explicit fresh builds and
tests using another C toolchain bypass the shared runner. Tests that deliberately
compile an independent runner still do that work; suite sharing does not remove
the one-time build cost when compiler sources or the bootstrap change.

All active Python test drivers remain independently executable as
`python tools/test_<name>.py`. The runner runs them sequentially in sorted
order, using a separate process group and a configurable timeout per driver.
It reports failures while continuing unless `--fail-fast` is given.

`--group` is repeatable and selects the union of the named groups:
`smoke`, `frontend`, `mir`, `modules`, `language`, `runtime`, `tooling`.
Some drivers belong to more than one group. Repeated `--match` patterns
select by filename/stem, `--exclude` removes matching drivers, and those
filters combine with group selection. `--list` previews the final selection;
`--timeout 0` disables the per-driver timeout (default 600 seconds).
The runner does not forward driver-specific options such as `--jobs` or
`--rebuild`; invoke an individual driver for those controls.

The cheap `smoke` group checks the source module graph, documentation links,
fixture pairing and test-runner helpers without building a C compiler.
The full suite includes costly native builds, bootstrap fixed points, and
MIR/native comparisons. The internal fixture check does **not** execute all
proposed language-design cases. For self-hosting evidence, run
`python tools/test_mir_selfhost.py` and
`python tools/generate_bootstrap.py --check` as appropriate.

Test inputs are described in [test organization](../tests/README.md).
`tools/generate_core_fixtures.py` and
`tools/generate_extended_fixtures.py` are manual fixture-authoring tools
that overwrite checked-in files; they are not test runners.

## Correctness and profiling

- Keep interpreter and generated-C behavior equivalent; add negative and
  aliasing tests for changes to ownership, unions or return paths.
- Preserve the C bootstrap fixed point and run
  `python tools/generate_bootstrap.py --check` before publishing it.
- Benchmark compiler stages via `tools/profile_mir.py` and MIR allocations via
  `tools/profile_mir_allocations.py`; for dictionary workloads use
  `tools/profile_runtime_dict.py` or `tools/benchmark_dictionaries.py`.
  Run `python tools/benchmark_stdlib_numeric.py --runs 5 --opt 2` to compare
  emitted-C `Std.Numeric` matrix operations with hand-written, shape-specialized
  flat-array loops. With `--baseline-numeric path/to/old/Numeric.sirius`, it
  also compares library changes against the previous implementation. The tool
  reports source generation and C build times separately from native execution,
  validates equal checksums, and alternates execution order after warm-up.
  Results include allocations, bounds checks and process startup; the flat
  loops do not perform general shape validation, so ratios do not isolate
  record overhead alone. Single microbenchmarks are not whole-compiler
  performance evidence.
  Run `python tools/benchmark_stdlib_enumerate.py --runs 5 --opt 2` to compare
  the current one-pass `enumerate` against the previous two-pass algorithm
  under the same compiler and array runtime. It includes startup and result
  checks, so it is a workload comparison rather than an isolated instruction cost.
- `python tools/test_runtime_scratch_arena.py` validates an isolated
  POD-only scratch allocator experiment; use `--benchmark` for synthetic
  allocation-count and CPU-time comparisons, and `--sanitize` to test with
  supported Clang/GCC sanitizers. It is not production runtime code.
- [Runtime](RUNTIME.md), [IR design](IR_DESIGN.md) and the
  [historical MIR profiles](history/MIR_PROFILE.md) provide detailed context.
